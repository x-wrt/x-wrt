# YT9224 support (Linux 6.18)

The `799-*` backports add the Motorcomm YT9215/YT9224 DSA driver,
YT8824 PHY support, and the native and four-byte YT922x taggers.
Source: [xwrt-flint4-adaptation, 70db39e1b1f2](https://github.com/Beaverfffan/xwrt-flint4-adaptation/tree/70db39e1b1f2d4dfa1f4a31a041913c162b2a8c8).
Original patch authorship is retained. Protocol value 32 remains reserved
for existing target-specific taggers; YT921x/YT922x/YT922x-4B use 33/34/35.

## Board integration

- Select `kmod-dsa-yt92xx` (which also selects the Motorcomm PHY module),
  or enable the corresponding kernel symbols in a built-in board configuration.
- Describe the MDIO switch with `compatible = "motorcomm,yt9224"`, its actual
  reset GPIO, user ports, PHY addresses, CPU port and Ethernet conduit.
- Set `dsa-tag-protocol = "yt922x_4b"` on the switch CPU port to use MediaTek
  NATflow/PPE. The default native eight-byte tag is supported in software;
  MediaTek TX checksum/GSO offloads are disabled for that native format.
- For a fixed 10G USXGMII switch link, set `mediatek,force-fixed-10g` on the
  MediaTek PCS node and configure matching fixed-link parameters at both ends.
  Ordinary in-band USXGMII links retain their existing behavior.

These changes supply drivers, not a complete Flint 4 board definition or image.

## NATflow/PPE

The MediaTek and ramips `995-0001` patches identify the tag protocol through
the conduit's DSA `tag_ops->proto`. For `YT922X_4B`, the DSA path check calls
`dsa_tag_yt922x_4b_standalone_vid(dp)` to generate the full control word
`BIT(port) << 5` and stores it directly in the 16-bit path field. PPE validates
that exactly one bit in bits 13:5 is set and recovers the physical port with
`__ffs(tag) - 5`. It inserts the unchanged control word after TPID `0x8100`.
Ports 0 through 8 are representable;
port 7 uses bit 12 and port 8 uses bit 13, so masking this word to a 12-bit
VLAN ID would lose the destination. Queue selection uses the raw port.

IPv4/IPv6 paths insert the CPU tag before an optional customer VLAN and PPPoE.
Native eight-byte tags and unsupported ports remain on the software path.
VLAN-filtering DSA ports are also excluded because the software tagger may
need to supply an access-port PVID that the PPE path does not carry.

X-Wrt's existing global DSA bridge-offload disable patch remains in effect.
The switch driver's bridge/FDB/MDB/VLAN callbacks do not by themselves enable
hardware bridge switching in this configuration.

## Validation boundary

Patch application, targeted kernel-object compilation and source-extracted
port/tag/encapsulation checks do not establish hardware correctness. Board
bring-up still needs bidirectional IPv4/IPv6 traffic, VLAN and PPPoE tests,
PPE bind counters, CPU utilization, and link recovery checks on the device.
